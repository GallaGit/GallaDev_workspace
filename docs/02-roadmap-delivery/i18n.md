# English As The Secondary Language

> **Status:** specified, not implemented · decision by Ociel, 26-27 Sep 2026 · **Updated:** 2026-09-27
> **Order:** second slice, after [`what-it-is.md`](./what-it-is.md) (ES: [`what-it-is.es.md`](./what-it-is.es.md)).
> Do not present this as current behavior. The interface is still Spanish today. The product rule “the user interface remains Spanish” is replaced by this decision; the code is not there yet.

## 1. Decision

Spanish stays the default language. English is the secondary language for the whole project.

It covers the UI of every page (including login and the What it is section), navigation, Kanban, statistics, settings, user-facing emails and templates, and error pages.

There is a visible language switcher. The choice is persisted (a cookie; proposed name `gdw_locale`, to confirm at implementation). Values are `es` and `en`. With no choice, or a value other than those two, the app uses Spanish.

## 2. Recommended approach

Marked **proposed, to confirm at implementation**:

- `next-intl`, or an equivalent for the App Router.
- Message catalogs `es.json` and `en.json`.
- No hardcoded UI strings on the surfaces in section 1.
- A missing English key falls back to Spanish. The raw key is not shown.

Stored status names (`Nuevo`, `Pendiente revisar`, `Validado`, `Email preparado`, `Email enviado`, `Respondió`, `Reunión`, `Cliente`, `Descartado`) stay the canonical values. Visible labels are translated. The Postgres enum and the stored `Origen` value are not translated as data.

The approved Qué es / What it is copy lives in that slice’s spec. This slice serves it from the catalogs; it does not rewrite it.

## 3. Phased plan

1. **Infrastructure and switcher.** Default locale `es`, cookie, visible switcher on login and on the authenticated shell, catalogs empty or with the first keys, fallback to Spanish.
2. **Page-by-page string extraction.** Login and What it is, navigation, Leads, Kanban, statistics, settings, and the rest of the app pages. Each page finishes with no hardcoded UI strings on that surface.
3. **Emails.** Templates a person sees, in both languages: the web-ingest receipt to the form submitter, the internal notice, and templates already in the product. Language follows the stored preference when one exists; otherwise Spanish.
4. **CI check.** A test or script fails when a key is in one catalog and missing from the other. Runtime fallback does not waive that check: it keeps silent gaps from sticking.

## 4. Acceptance criteria

Checkable once an implementation exists. None of them hold today.

1. With no cookie, or a value other than `es` or `en`, the UI is Spanish.
2. The switcher is visible on login (including What it is) and in the authenticated app navigation. Switching to English and reloading keeps English. The cookie is the persistence.
3. These surfaces have copy in `es.json` and `en.json`, and no leftover hardcoded UI strings: login, What it is, navigation, Kanban, statistics, settings, error pages (`error.tsx`, `global-error.tsx`).
4. The nine statuses are shown translated in English and are still stored as the canonical Spanish value.
5. The ingest receipt to the form email and the internal notice go out in the chosen language, and in Spanish when there is no choice. A template is not locked to one language.
6. A key present only in `es.json` does not break the screen: Spanish is shown. CI fails anyway, because the key is missing from `en.json` (and the reverse).
7. The What it is slice may already have shipped. This slice does not redraft that copy; it connects it to the switcher.

## 5. Out of scope

The language of AI-generated pain analysis stays an **open question**. It is out of this slice unless wiring it is trivial (for example, passing the already resolved locale into a call that already accepts a language). Text stored in `Análisis IA` is not migrated or rewritten here.

Also out: translating lead data (company, notes, city), the client portal as a product (when it exists, it uses this same switcher; not a third language), and billing.
